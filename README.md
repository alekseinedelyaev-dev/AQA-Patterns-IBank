
# Домашнее задание «2.3. Patterns»

## Задача № 2. Тестовый режим интернет-банка

[![Java CI with Gradle](https://github.com/alekseinedelyaev-dev/AQA-Patterns-IBank/actions/workflows/gradle.yml/badge.svg)](https://github.com/alekseinedelyaev-dev/AQA-Patterns-IBank/actions)

## Описание проекта

Проект представляет собой автоматизированное тестирование
авторизации пользователей интернет-банка.

Тестирование выполняется с использованием Selenide,
JUnit 5 и REST-assured.

Для создания тестовых пользователей используется API
банковского приложения.

Данные пользователей генерируются автоматически
с помощью Java Faker и сохраняются в data-классах,
реализованных с использованием Lombok.

## Реализованные автотесты

В проекте реализовано 8 сценариев тестирования авторизации.

1. Успешный вход активного пользователя с правильным
   логином и паролем.

2. Проверка отказа в авторизации заблокированному
   пользователю с правильными учётными данными.

3. Проверка авторизации активного пользователя
   с неправильным паролем.

4. Проверка авторизации активного пользователя
   с неправильным логином.

5. Проверка попытки входа пользователя,
   который не зарегистрирован в системе.

6. Проверка авторизации заблокированного пользователя
   с неправильным паролем.

7. Проверка авторизации заблокированного пользователя
   с неправильным логином.

8. Проверка авторизации активного пользователя
   с одновременно неправильными логином и паролем.

## Проверяемые результаты

При успешной авторизации активного пользователя
открывается страница «Личный кабинет».

При попытке входа заблокированного пользователя
с правильными данными отображается сообщение:

«Ошибка! Пользователь заблокирован».

При использовании неправильного логина или пароля
отображается сообщение:

«Ошибка! Неверно указан логин или пароль».

Автотесты проверяют сообщения об ошибках
и отсутствие доступа к личному кабинету.

## Генерация тестовых данных

Для генерации тестовых пользователей используется
класс DataGenerator.java.

Генератор создаёт случайные логины и пароли,
а также позволяет зарегистрировать пользователей
со статусами:

- active — активный пользователь;
- blocked — заблокированный пользователь.

Для регистрации пользователей через API используется
POST-запрос:

POST /api/system/users

При успешной регистрации проверяется HTTP-статус 200.

Для преобразования Java-объектов в JSON
используется библиотека Gson.

## Запуск банковского приложения

Для работы с API необходимо запускать приложение
в специальном тестовом режиме.

Команда запуска:

```bash
java -jar ./artifacts/app-ibank.jar -P:profile=test
```

После запуска приложение доступно по адресу:

http://localhost:9999

Важно: без параметра -P:profile=test API создания
пользователей будет возвращать HTTP 404.

## Запуск автотестов

Перед запуском автотестов необходимо убедиться,
что банковское приложение запущено.

### Windows

```powershell
.\gradlew.bat test "-Dselenide.headless=true" --info
```

### Linux

```bash
bash ./gradlew test --info -Dselenide.headless=true
```

## GitHub Actions

В проекте настроена автоматическая проверка
с использованием GitHub Actions.

При отправке изменений в ветку main:

1. Загружается исходный код проекта.
2. Устанавливается JDK 17.
3. Запускается интернет-банк в тестовом режиме.
4. Проверяется готовность приложения.
5. Выполняются автоматизированные тесты.
6. Формируется отчёт о результатах.

Статус последней сборки отображается
в бейдже в начале README.

## Сравнение времени тестирования

**Время, затраченное на ручное тестирование (минут):**
30 (ориентировочная оценка).

**Время, затраченное на автоматизацию (минут):**
60 (1 час).

Время автоматизации включает:

- подготовку тестового проекта;
- настройку необходимых библиотек;
- создание генератора тестовых данных;
- реализацию API-регистрации пользователей;
- написание автотестов;
- исправление ошибок и отладку;
- запуск и проверку результатов.

Время ручного тестирования оценено для выполнения
аналогичных восьми сценариев с использованием
браузера и Postman.

Автоматизированное тестирование требует
больше времени на первоначальную подготовку,
но позволяет значительно ускорить повторные проверки.
